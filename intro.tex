\section{Introduction}
\label{sec:intro}
\label{firstcontentpage}

Programming often involves reasoning about static types.
Development tools assist programmers in limited ways with this task, 
e.g. by reporting the type of an expression when hovering over it, or reporting the expected and actual type when there is a type error.
However, these services only report \emph{what} the type of an expression is, not \emph{why} it is that type 
in the context of the surrounding program.
Programmers must hunt through the program themselves to answer these questions, and the program often contains a large volume of code irrelevant to their query.

This {paper} develops the theory of \textit{type slicing} from type-theoretic first principles. Type slices allow developers to ask ``why questions''~\cite{developers-ask-why-questions} about type information reported about arbitrary terms within a (possibly incomplete or erroneous) program. The answers are given in the form of a minimal slice of the original program (i.e. a program with unrelated terms folded away) that suffices to reproduce the queried type. 

Type slicing is inspired in principle by prior work on program slicing (reviewed in detail in \cref{sec:related-work}), in particular, lattice-based \textit{Galois slicing}~\cite{Perera2012,Ricciotti2017,PereraGarg2016,PereraVis2022,AtkeyPerera2025}. However, slicing is here applied to a (non-Galois) static type checking setting, loosely more akin to type-error slicing~\cite{Wand1986,HaackWells2003,TipDinesh2001} (but our model also explains well-typed programs), and the concurrent independently researched work on \emph{type-directed slicing}~\cite{TypeDirectedSlicing} for Java.

We consider the problem of type slicing in the context of \emph{bidirectional type systems}~\cite{BidirectionalTypes}, which distinguish \emph{type synthesis} (which type does this term have) from \emph{type analysis} (which type is expected).
Correspondingly, a \textit{synthesis slice} (\cref{sec:synthesis}) of a selected term answers ``which parts of the program caused it to have type $\tau$?'' and an \textit{analysis slice} (\cref{sec:analysis}) answers the complementary question, ``which parts of the surrounding program enforced that this term have type $\tau$?''

Queries can be \textit{refined}, say from an entire function type to just its codomain, resulting in a smaller slice. This allows a programmer to incrementally focus on sub-parts of the type that are of interest. For example, maybe after some exploration, the programmer determines that only a small region of a large record type involved in a type error is erroneous.

The type slicing machinery applies equally well to well-typed and ill-typed terms. In the case of ill-typed terms, it provides a mechanism that may aid in debugging type errors.

A broad literature attacks the complementary problem of diagnosing type \emph{errors}, especially in globally-inferred (Hindley-Milner) languages where inference offers no natural home for the blame. One line improves \emph{localisation}, recasting error attribution as finding a minimum-weight or most-likely set of constraints to blame~\cite{ZhangMyers2014,PavlinovicKingWies2014}. A \emph{counter-factual} line instead reports the program edits that would make the program type-check, presenting diagnosis as a menu of candidate fixes~\cite{ChenErwig2014,LernerSeminal2007}. Interactive and algorithmic-debugging tools let the programmer navigate the inference derivation, answering questions to converge on the mistake~\cite{Chitil2001,StuckeyChameleon2003}. Others leave the static setting entirely, executing the ill-typed program to produce a concrete dynamic witness of the inconsistency~\cite{SeidelJhalaWeimer2016}. Each of these produces a \emph{diagnostic} (a localisation, a suggested edit, a witness) rather than a reduced program, and targets the single fixed question of why a program fails to type-check.

A distinguishing feature of type slicing is that a slice is itself a valid incomplete program that preserves the original's shape; in Hazel, which allows incomplete programs, this is simply a valid program. Type slicing therefore \emph{composes} with these methods rather than competing with them: because the minimised slice remains a well-formed program retaining the queried type information, any existing type debugging technique can be run directly on the reduced program, combining the benefits of both methods.

\subsection{Contributions}
\label{sec:scope}
The theory contributed by this paper applies to \textit{bidirectional type systems} with any form of \textit{downwards static graduality} (\cref{sec:gradual-types}) on expressions, inspired by the gradual typing literature~\cite{GradualRefined} extended to incomplete programs, i.e. programs with holes and marked errors. In particular, the formal development is based on the Hazelnut calculus~\cite{Hazelnut2017} and subsequent work on the marked lambda calculus~\cite{Marking2024}. Notably, we do \textit{not} require any cast dynamics like in gradual type systems, meaning type slicing is applicable to any bidirectional system only by assigning an appropriate precision relation on types and terms (\cref{sec:core-lattice}).
The core calculus for type slicing and accompanying metatheory developed in this paper has been mechanised in Agda. This development is available in the supplemental material.

An example full-scale language which satisfies these conditions is Hazel~\cite{hazel-website}, whose implementation we have extended with an efficient linear-time approximation of type slicing. This implementation, which we introduce by example in \cref{sec:slicing-by-example}, is available in the supplemental material. We do not make any specific claims about the usability of the prototype user interface presented in this paper; it is intended only as an initial proof of concept. We expect the theory contributed by this paper to allow a variety of user interfaces for type debugging and explanation to be developed and evaluated in practice. We suggest several avenues for exploration by the community in \cref{sec:further-work}. For example, recent work~\cite{TypeDirectedSlicing} developed a \emph{type-directed} slicer for Java and evaluated it as an aid for debugging type checkers \emph{themselves}, by reducing bug reports against large codebases to small type-behaviour-preserving test cases; we discuss how this relates to type slicing in \cref{sec:related-work}.
