Section 10 discusses ranking between minimal slices, establishing that

minimising the number of non-hole branches remaining in the slice). We
settle at just finding any minimal slice, as the focus of this paper
is on mathematically describing this _entire class_ of solutions (and
approximating at least one efficiently); choosing between minimal
slices becomes more subjective: e.g. /is a slice with fewer branches,
containing large tuples, more 'comprehensible' than a 'smaller' slice
with partially omitted tuples over several branches?/

** Reviewer C
Using plain slicing to understand the types of a program is an
interesting idea, and does work reasonably well in a few cases. For
example a chain of bindings sourced from some annotated function
parameter.

However, these generally produce overapproximations, or
underapproximations (bad!!) for some slicing methods, among some other
disadvantages:
- Some slicing methods may not even retain types in their slices at
  all. And most (but not all) don't allow selecting any 'term', but
  rather only variables as the criterion.
- There is no notion of 'refining' type queries, we can only look at
  the terms / variables.
- Data flow retains much more information than is required by just the
  types, for example a function application ~f(e)~ has it's return
  type sourced from only the function ~f~ (in our setting at least),
  but plain slicing may retain ~e~ too.
- Any situation where types are defined by annotations, we can omit
  the term itself (but plain slicing would not, it relates to the
  values).
- If statements will keep the guards & multiple branches (in static
  slicing), type slicing will only retain branches without (fully)
  redundant types.
- For dynamic slicing methods, the branch taken in reality may not
  even contain all the type information (with gradual types), so would
  not produce a valid type slice.

On *(2)*, adding annotations in inferred languages (where these type
error slicing tools generally are made for) typically changes the
constraints / typing derivation that exists, meaning the explanation
may not be the same (may use information from the annotation
itself), or may even produce multiple error slices!

For example, (in most bidirectional systems) asking the type of a branching
statement by annotation would produce several errors on each branch,
all with their own error slices. In a case where type information is
derived from multiple branches, you may need to inspect multiple of
these error slices to explain the error, and there is no omission of
redundant type information between these multiple slices (only per
individual slice).

It's probably not infeasible to adapt an existing system to work
outside of errors by using techniques like this, but you would still
lose the refining queries feature, and would need to apply some
existing method to a bidirectional typing system.
