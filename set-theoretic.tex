\subsection{Set-Theoretic Types}
\label{sec:set-theoretic}
\label{sec:future-set-theoretic-occurrence}

Type slicing looks especially promising for common type systems in which \textit{control flow and types are intertwined}: an expression's type depends non-trivially on the branches inside a function, or the control-flow path in which the expression lies. Explaining a type then genuinely requires considering the branches within the code, rather than just annotations and literals; as type slices necessarily \textit{retain} program structure, they can retain the appropriate control flow structure.

\emph{Set theoretic types} extend the type language with union, intersection, and negation, letting a term carry several types simultaneously, typing overloaded functions and typecase constructs common in real world hybrid typed languages (e.g.\ TypeScript, or Elixir~\cite{ElixirTypes}). Relevant foundations have been explored~\cite{CastagnaLanvin, CastagnaLPS}, with the refined criteria for gradual typing proved for gradual intersection types~\cite{AngeloThesis}, and with reconstruction algorithms now inferring such types for unannotated dynamic code~\cite{CastagnaLN2024}, ready in theory for type slicing to build upon.\footnote{After adapting into a bidirectional setting with expression holes.}

\paragraph{Example.} Consider generalising sum types of the core calculus (\S\ref{sec:core-calculus}) to allow sum injections to synthesise partially dynamic types: when $\synthesis{e}{\tau}$, let $\synthesis{\iota_1\; e}{\tau + \gap}$ and $\synthesis{\iota_2\; e}{\gap + \tau}$.
Then an if statement $\mathit{pred} \triangleq \mathbf{if}\ x > 0\ \mathbf{then}\ \iota_1(x - 1)\ \mathbf{else}\ \iota_2(())$ synthesises a sum type $\mathbb{N} + 1$ without requiring annotations, much as union type inference works (i.e. union type $\mathbb{N}\ |\ 1$), and type slicing can explain where each component comes from: querying $\gap + 1$ highlights exactly the false branch, and $\mathbb{N} + \gap$ the true one. We mechanised this example.

In fact, some forms of set-theoretic type inference are particularly closely related to type slicing methods. For example, in \citet{CastagnaLN2024}, the environment refinement driving their split propagation asks what assumptions make an atom have a demanded type, similar to the idea behind minimal assumptions in type slicing. These inference systems do not track the code provenances sourcing the types, but the similarities suggest that adding this would give a way to implement some elements of synthesis type slicing.

\subsection{Occurrence Typing}
\label{sec:occurrence}

\emph{Occurrence typing}~\cite{OccurrenceTyping} is another common technique in hybrid type systems. Inside the true branch of \texttt{if (typeof x = int) ... else ...}, the type of \texttt{x} is refined as an \texttt{int}. These explicitly require exploring the surrounding control flow, which can be extensive, to reason about the types. As type slices necessarily retain program structure, they can provide a reduced slice with minimal control flow to reason within. Formally applying type slicing to such systems will, however, need extensive integration work with bidirectional typing and the DSGG.
